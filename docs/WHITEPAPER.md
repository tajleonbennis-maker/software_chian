## 1. 我们在做什么

### 1.1 一句话

**基于网络空间测绘数据，自动发现公网暴露的热门开源组件与 API 风险，产出安全研究人员可每日消费的情报简报与可复核结论。**

我们不是又一个「只会扫端口、堆资产数字」的平台，而是把研究员日常工作——

> 查测绘 → 认组件 → 判风险 → 出结论 → 可复核

——尽量**自动化、规模化、可复现**。

### 1.2 要回答的三个问题

1. **什么暴露在外面？**  
   热门组件 / 热门开源项目（如 Dify、Open WebUI、DeepTutor、1Panel 等）在公网的部署与版本分布。

2. **哪些有真实风险？**  
   指纹测准 → 漏洞匹配（区分「疑似」与「已复验」）→ API 发现 → 密钥 / SK 泄露检测。

3. **现在该做什么？**  
   高危告警、专项分析、带证据与行动建议的研判简报——而不是只给人一张大表。

### 1.3 我们刻意不做的事

- 不追求「扫全网、资产越多越好」；默认对每个研究主题**限量深挖**（如约 100 个样本）。
- 不把 Dashboard 图表当作产品本身；**主交付物是简报、专项报告与可行动告警**。
- 不在证据不足时宣称「已确认漏洞」；对外口径强制区分**疑似匹配**与**已复验**。
- 不把系统定位为攻击教程分发或未授权扫描工具；仅用于授权研究与自身暴露面情报。

## 2. 为谁而做

### 2.1 核心用户

| 用户 | 场景 |
|------|------|
| **安全研究人员 / 安全运营者**（当前阶段首先是项目所有者本人） | 每天想知道：热搜组件有无新风险、某开源项目公网暴露是否高危、告警该不该跟 |
| 小团队安全运营（下一阶段） | 需要可转发简报、可分工告警、可引用的证据包 |

### 2.2 典型使用场景

1. **早上一分钟**：今日情报简报——今天最值得看的 1～3 件事。  
2. **研究某组件**（如 Dify）：版本分布、高危命中、FOFA 语法、复验情况。  
3. **收到告警**：证据摘要 + 置信度 + 建议动作（复核 / 关注 / 可忽略）。  
4. **对外说明**：可复核证据链（来源、时间、样本、查询语法），而不是「信我扫到的数字」。

### 2.3 用户不需要的

- 单纯「又多了 2000 条资产」而没有优先级。  
- 无法解释口径的华丽大屏。  
- 无法独立验证的「全网结论」。

## 3. 产品理念

### 3.1 测绘视角的供应链安全

传统 SCA / SBOM 回答的是：*我构建的软件里有什么组件？*  

本产品从**外部可观测攻击面**出发：*互联网上实际跑着什么组件、什么版本、暴露了哪些 API、有没有把密钥打在公网？*

两者互补。我们聚焦后者，并与供应链、API、凭据泄露结合，形成「外部软件供应链情报」。

### 3.2 产品驱动，而非能力驱动

| 错误路径 | 正确路径 |
|----------|----------|
| 有什么扫描能力就堆什么 | 用户要什么结论，再倒推能力 |
| 先做完所有引擎再谈交付 | 先定义简报 / 报告长什么样 |
| 数字即价值 | **情报** = 面向决策者的、有结论、可行动、可复核的信息 |

### 3.3 安全大脑 + 执行引擎

| 角色 | 职责 |
|------|------|
| **安全大脑** | 思考与指挥：选题、判断、调度、汇总、写简报与告警 |
| **执行引擎** | 干活：指纹、探测、API 遍历、密钥扫描、存活复验；只回传证据，不擅自发布结论 |

**三条戒律：**

1. 没有任务单，引擎不主动开扫。  
2. 没有来源与置信度，大脑不把结论写进简报。  
3. 没有行动建议，尽量不发告警。

## 4. 系统架构

### 4.1 逻辑架构

```text
                    ┌─────────────────────────────────────┐
                    │           安全大脑（控制端）           │
                    │  选题 · 调度 · 研判 · 存储 · 汇报      │
                    │  研究大脑 / Dispatcher / Dashboard    │
                    │  AI 辅助分析 · 告警 · 简报             │
                    └──────────────────┬──────────────────┘
                                       │ 任务下发 / 结果回传
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
       ┌────────────┐           ┌────────────┐           ┌────────────┐
       │ 执行引擎 A  │           │ 执行引擎 B  │           │ 执行引擎 C  │
       │ 深度分析    │           │ 代理探测    │           │ 代理探测    │
       └────────────┘           └────────────┘           └────────────┘
```

### 4.2 指挥闭环

```text
观察 → 思考（今日 Top 1～3 问题）→ 下令（任务单）
  → 引擎执行并回传证据 → 复盘（置信度 / 疑似vs已复验）
  → 交付（简报 / 告警）→ 必要时再次复验
```

### 4.3 数据与分析主链路

```text
测绘数据（FOFA 等）
  → 资产入库（限量、可追溯）
  → 技术指纹 / 组件识别
  → 漏洞匹配（疑似）
  → 主动复验（已复验）
  → API 发现 / JS 与面板探测 / 凭据（SK）检测
  → 研判与优先级
  → 简报 · 专项报告 · 告警
```

### 4.4 部署形态（概要）

- **大脑节点**：调度、存储、AI 分析、Web Dashboard、对外 API。  
- **多个 Worker 节点**：按任务执行扫描与回传。  
- **访问**：内网 Dashboard + 可选公网入口（需认证）。  
- **研究阶段**：以可备份的数据存储为主；明确备份与恢复预期，不夸大高可用。

> 具体主机与端口以仓库部署文档及运行环境为准，白皮书只描述角色，避免与瞬时运维状态强绑定。

## 5. 核心能力

### 5.1 发现与选题

| 能力 | 说明 |
|------|------|
| 测绘资产发现 | 对接 FOFA 等，按研究主题拉取样本（求质不求量） |
| 热搜驱动 | 跟踪测绘平台热门组件/产品信号，自动进入研究队列 |
| 开源热点（规划/增强） | 结合热门 GitHub 项目等，扩展「研究什么」的供给 |

### 5.2 识别与分析

| 能力 | 说明 |
|------|------|
| 技术指纹 | Web 服务器、框架、面板、AI 应用等组件识别 |
| 多组件视角 | 一个暴露面往往由多个组件构成，支持分组件观察 |
| 漏洞匹配 | 离线规则 + 公开漏洞情报补充；版本区间命中 |
| 口径拆分 | **疑似**（匹配）与 **已复验**（含主动探测证据）分开统计与表述 |
| API 遍历 | 从页面/JS/已知面板路径发现 API，观察未鉴权与敏感暴露 |
| 凭据检测 | 识别疑似 API Key 等；展示默认脱敏；完整内容受权限保护 |

### 5.3 交付与行动

| 能力 | 说明 |
|------|------|
| 资产详情 | 组件、漏洞、API、敏感信息等结构化详情 |
| 供应链健康视图 | 高风险组件、暴露分布等汇总（持续迭代） |
| 组件专项 | 如 Dify：版本分布、高危要点、一键查询语法 |
| 告警 | 高危 / 凭据类事件推送（脱敏、去重、冷却） |
| 每日简报（产品主目标） | 人类可读的「今天该看什么」 |
| 可复核证据 | 来源、时间、置信度、可复制查询语法、证据摘要 |

### 5.4 智能辅助

- 研究大脑：自动选题与研究任务编排。  
- 大模型辅助：用于洞察归纳与简报起草，**不作为唯一真相源**；关键结论仍依赖证据与口径规则。  
- 对话式任务入口（如自然语言触发研究/扫描），便于运营。

## 6. 情报可信度标准

研究型系统最容易被质疑的是：「你的数字我无法验证。」我们采用以下硬标准：

| 维度 | 要求 |
|------|------|
| 来源可追溯 | 每条资产/结论标注来源（测绘/主动探测/节点等） |
| 时效 | 首次发现时间、最近验证时间；长期未复验降为历史观测 |
| 置信度 | high / medium / low（与指纹强度、是否复验相关） |
| 口径分离 | 疑似与已复验分列；未复验不得表述为「已确认存在漏洞」 |
| 可复核 | 提供可复制的测绘查询语法与关键证据摘要（不含完整密钥） |

**推荐对外表述模板：**

> 截至 {time}，在样本集 {n} 中观测到 {component} {version} 暴露 {count} 例；其中 {x} 例完成主动复验，置信度 {level}。

避免使用「全网共有 xxx 个漏洞资产」这类无法由测绘样本支撑的表述。

## 7. 产品形态与路线图

### 7.1 主产品形态（优先级）

| 形态 | 用户价值 | 优先级 |
|------|----------|--------|
| 每日情报简报 | 1 分钟知道今天看什么 | P0 |
| 高危告警（含证据与建议） | 实时/准实时响应 | P0 |
| 组件专项报告 | 深入理解某一热门组件 | P1 |
| 可复核证据包 | 对外证明与协作 | P1 |
| 工作台 Dashboard | 钻取与运营 | 支撑能力，非门面 |

### 7.2 近期聚焦（最小闭环）

```text
研究大脑选题
  → 产出当日研判简报（短、可行动）
  → 高优先级项附证据摘要 + 行动建议 + 查询语法
  → 推送到用户（如 Telegram，凭据脱敏）
```

**成功标准（示例）：**  
用户连续多日能收到简报，并至少有一次据此打开详情或进行复核/处理标记——说明结论在被使用，而不仅是系统在空转。

### 7.3 中期增强（不挡主路径）

- 热门 GitHub 与开源安全情报告题增强。  
- 轻量 SBOM / 组件字段补全（如 Syft/Trivy 类能力按需接入）。  
- 凭据加密存储与访问审计强化。  
- 风险状态机：observed → verified → notified（及后续处置状态）。

### 7.4 长期可选（专项验证，非默认主线）

- 受控靶机复现：仅对高优先级组件做可复现验证，写入报告证据章节。  
- 蜜罐观测：观察真实攻击手法；与测绘资产分口径、分库管理。  

上述能力若开展，仍服从「大脑指挥、引擎执行」，不另起独立产品叙事。

## 8. 安全与合规原则

1. **授权与用途**：仅用于合法授权的安全研究、自身资产与公开情报分析；禁止未授权扫描与攻击。  
2. **敏感数据**：API Key 等凭据默认脱敏展示；完整读取需鉴权；推送通道不发送完整密钥。  
3. **访问控制**：管理面与 API 使用令牌/认证；公网入口需额外保护。  
4. **节点信任**：执行引擎回传需可校验（任务 ID、节点身份等），高危结论宜结合复验。  
5. **表述诚实**：区分样本集与全网、疑似与已复验，避免误导性传播。

| 威胁情报平台 | 可消费少量「在野关注」信号用于选题，不自建全能 TIP |

## 10. 总结

| 维度 | 定义 |
|------|------|
| **做什么** | 测绘驱动的供应链 · API 安全情报 |
| **为谁做** | 安全研究员 / 运营者（先服务真用它做决策的人） |
| **怎么做** | 安全大脑思考指挥 + 多引擎执行 |
| **交付什么** | 简报、专项报告、带证据的告警 |
| **如何可信** | 来源、时效、置信度、疑似/已复验、可复制复核 |
| **如何成功** | 结论被人使用并促进行动，而不是资产表数字增长 |
