# 仓库维护规范（CyberStroll）

> 目标：让仓库持续**可理解、可信任、有进展**，从而获得关注与协作。  
> 维护不是堆功能，而是维持「产品叙事 + 可见进展 + 专业披露」。

---

## 1. 角色

| 角色 | 职责 |
|------|------|
| 项目所有者 | 合并代码、部署、最终决策、对外发帖 |
| WorkBuddy 等实现助手 | 开发、调试、落 Issue |
| 文档 / 叙事协作者（如 Grok） | README、白皮书、Changelog、Issue 文案、披露稿 |

---

## 2. 每周节奏（建议）

| 动作 | 产出 |
|------|------|
| 同步运行数据 | 资产量、告警是否送达、1 个有价值发现 |
| 更新 Changelog「Unreleased」 | 人话进展，避免纯内部 commit 列表 |
| 回复开放 Issue | 24～48h 内有响应 |
| 可选：1 条对外观察 | X / 博客 / Issue 研究笔记（脱敏） |

---

## 3. 每月节奏

- 打一个 GitHub Tag / Release（哪怕是 `v0.1.x-research`）
- 勾选白皮书路线图
- 回顾：Star、Issue、上游披露反馈
- 检查安全：示例中是否误含完整密钥、演示环境鉴权是否正常

---

## 4. 文档真源

| 文档 | 真源用途 |
|------|----------|
| `README.md` | 30 秒理解项目 |
| `docs/WHITEPAPER.md` | 产品宪法 |
| `CHANGELOG.md` | 对外进展 |
| `docs/MAINTENANCE.md` | 本维护规范 |
| GitHub Issues | 决策与任务跟踪 |

原则：**Issue 可以吵，白皮书与 README 必须一致。**

---

## 5. 发版检查清单

- [ ] README 阶段标签与事实一致  
- [ ] CHANGELOG 有对应版本小节  
- [ ] 无明文密钥、无未授权利用步骤  
- [ ] 安全相关结论带「疑似/已复验」或样本集表述  
- [ ] 破坏性变更在 Changelog 标明  

---

## 6. 增长相关（允许做 / 禁止做）

**允许**

- 责任披露、方法论分享、脱敏案例  
- 清晰架构图与简报样例  
- 与上游开源项目协作修配置问题  

**禁止**

- 公开完整 API Key / 会话 Cookie  
- 鼓励未授权扫描或利用  
- 用「全网 xxx 漏洞资产」等不可复核话术拉关注  

---

## 7. 协作口令（给 AI 助手）

所有者可直接下达：

- `更新 README 进展区`  
- `写本周 Changelog`  
- `起草责任披露`  
- `根据 Dashboard 写研究观察 Issue`  
- `准备 Release 说明`
